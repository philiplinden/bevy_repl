## What the docs ask for

Distilled from the vision (`doc/src/design/index.md`), `commands/index.md`,
`features/default_commands.md` and `how_it_works/logging.md`:

1. **One-line setup.** Add `ReplPlugins`, nothing else changes. Works with
   `DefaultPlugins` or `MinimalPlugins`, headless or windowed. (Vision 1, 6, 8.)
2. **Commands feel like a normal CLI.** Describe them with clap (builder or
   derive), register with `.add_repl_command::<C>()`, handle with
   `.add_observer`. The command struct is the event.
3. **Built-ins:** `quit` (`q`, `exit`), `help`, `clear`, each behind a
   feature flag.
4. **Output goes to stdout and stays after exit.** (Vision 2.)
5. **Purely additive.** Bevy's logs and `println!` keep working unchanged.
   (Vision 3, and `logging.md`: "integrates with Bevy's `LogPlugin` without
   additional setup".)
6. **Typing commands doesn't trigger key presses in the game.** (Vision 4.)
7. **The terminal is always restored** on `quit`, Ctrl+C or panic.

**Not now:** runtime toggling (`commands/index.md`: "not possible to toggle the
REPL on and off at runtime (yet!)", matching the 08-28 decision), command
history, completion, custom prompt, configurable keybinds (already in

## Sanity check: is the vision possible without ratatui?

Before going further with the docs, check that a log area above a pinned
input row is achievable at all. The worry: a terminal has one cursor, and logs
have to print above the prompt while someone is typing in it.

Checked against the installed crate sources:

- **Bevy** (`bevy_log-0.20.1/src/lib.rs:367`): with no `fmt_layer` set, the
  logger is `fmt::Layer::default().with_writer(std::io::stderr)`. It writes
  wherever the cursor happens to be and knows nothing about a prompt. Only
  replacing `fmt_layer` changes that.
- **crossterm 0.28.1, Unix**: raw mode is `cfmakeraw`, which also clears
  output post-processing. That's the `\n` stair-stepping.
- **crossterm 0.28.1, Windows**: raw mode only clears
  `ENABLE_LINE_INPUT | ENABLE_ECHO_INPUT | ENABLE_PROCESSED_INPUT`. Output is
  untouched, so no stair-stepping.
- **crossterm** has `SavePosition`/`RestorePosition`, `Hide` and `ScrollUp`,
  but no scroll-region command. DECSTBM is written by hand, as `print.rs`
  already does.
- **clap** never touches the terminal. It's not part of this question.

Answer: **one cursor is enough, and ratatui isn't required.** Every tool with
this layout works the same way: writes are short and serialized, so the cursor
jumps to the log area, writes, and jumps back, and it looks simultaneous.

Ratatui also wouldn't solve it on its own. Its inline viewport with
`Terminal::insert_before` is this exact layout, but only for text routed
through ratatui. Bevy's logger would still write to stderr behind its back,
which is why the old README said logs only worked "if you disable Bevy's
`LogPlugin`". Line editors (rustyline, reedline) have the same limit on their
external printers.

Two ways to do it without ratatui:

- **A. Route all output through one writer** that erases the prompt, prints,
  and redraws. Robust, but Bevy's logs have to reach it: either through
  `LogPlugin.fmt_layer` (ADR 0003, breaks vision item 8) or by capturing
  stdout/stderr through a pipe (no `LogPlugin` change, but heavier,
  platform-specific, and panic output lands in the pipe).
- **B. Leave the real cursor in the log area** (the idea below). The only
  option that keeps item 8 without pipes. Risks: a log write landing mid-redraw
  (holding the stderr lock should prevent it for Rust writers), DECSTBM support
  and performance across terminals (microsoft/terminal#7019), and nothing has
  been tried in a real terminal yet.

## Spike: prove option B in a real terminal

A throwaway `examples/spike_prompt.rs` that doesn't use `ReplPlugins`, built up
in runnable steps:

0. `MinimalPlugins` at 60 fps plus `LogPlugin::default()`, logging
   `info!("tick {n}")` every 100 ms. Baseline: normal logging.
1. Startup: raw mode, make a blank bottom row (`\n` then `MoveUp(1)`), set the
   scroll region inside `SavePosition`/`RestorePosition` (DECSTBM moves the
   cursor home), hide the real cursor.
2. Input in `PreUpdate`: poll keys, edit a buffer, Enter logs the line, Ctrl+C
   sends `AppExit`.
3. Draw the prompt every frame while holding the stderr and stdout locks:
   save, move to the bottom row, clear, draw, reverse-video fake cursor,
   restore. Clean up on `AppExit`.
4. Stress test: log every frame, a multi-line log, and a `println!` thread
   outside Bevy, while typing fast. Watch for escape-code fragments, writes on
   the prompt row, flicker and stair-stepping.
5. Optional: resize the window; run on Linux to confirm the stair-stepping
   (output post-processing is not restored yet).

## Pitfall: Windows and Unix behave differently

The plugin can behave differently on Windows than on Linux and macOS. In past
sessions I was fixing bugs back and forth without realizing the cause was
switching operating systems between test runs. A fix that looked right on one
machine "broke" on the other, and it was very confusing.

macOS should behave like Linux here: crossterm uses the same Unix backend
(termios, `cfmakeraw`) for both.

Differences known so far:

- **Raw mode and output.** On Unix, raw mode also turns off output
  post-processing, so a plain `\n` stair-steps. On Windows, raw mode only
  changes input flags and `\n` behaves normally.
- **Key events.** Windows reports key releases as well as presses, Unix only
  reports presses by default. That's why input filters for `Press | Repeat`.
- **Earlier observation** (`dev/known_issues.md`): on Windows the cursor and
  typed text weren't visible in the prompt, while on Linux they were.

Rules from now on:

- Every test result in this log says which OS and terminal it came from.
- A bug isn't fixed until it's checked on both Windows and a Unix machine.
- Call this pitfall out in the book too, probably in `dev/known_issues.md` or
  `dev/build_tips.md`. Decide where during the doc walk-through.

## Idea, not decided: rethinking the logging seam

Re-reading the vision in `doc/src/design/index.md`, items 3 and 8 are the
binding constraints:

> 3. not conflict with nominal logging or printing to the terminal stdout;
> 8. not require disabling Bevy features or changing the base setup

ADR 0003 and all three options from 09-02 break item 8. The 09-02 note
identified the real problem precisely: Bevy's logger writes wherever the
cursor is, and the cursor is parked on the prompt row. Plus, on Unix, raw mode
turns off output post-processing, so `\n` stair-steps.

Both of those are terminal problems, so try fixing them in the terminal
instead of in tracing:

- **Keep the real cursor inside the scroll region.** Draw the prompt with
  save-cursor / move to the bottom row / draw / restore-cursor, and paint the
  editing cursor ourselves (reverse video). Anything that writes to
  stdout/stderr, whether Bevy's logger, a `println!`, or our own output,
  lands in the scroll region and scrolls above the prompt on its own.
- **Turn output post-processing back on after entering raw mode (Unix).**
  Raw mode is for input. Restoring `OPOST|ONLCR` means a plain `\n` behaves
  normally again. Windows raw mode only touches the input console mode, so
  there is nothing to undo there.
- **Serialize prompt redraws against log writes** by holding the
  stdout/stderr locks while redrawing. `tracing-subscriber`'s fmt layer
  writes each event with one `write_all` on `Stderr`, which takes the same
  lock.

If this holds up, `bevy_repl` never touches the global subscriber, never
touches `LogPlugin`, and drops `tracing-subscriber` as a dependency.
`RUST_LOG`, `LogPlugin { filter, level }` and custom layers all keep working
because we aren't in that path at all.
