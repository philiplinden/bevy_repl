# 2026-08-27

The `bevy_ratatui` crate has not been updated to Bevy 0.19 in a while. There is
a PR that compiles with `bevy_repl` on Bevy 0.19, but as it is not a published
version of the crate (it is a fork) we cannot publish a new version of
`bevy_repl` to crates.io.

We don't really need all the features of ratatui to do what we want. The hard
work is done by `crossterm` and `clap`. The `bevy_ratatui` crate provides a
convenient integration layer into Bevy.

So what if we could integrate with Bevy without ratatui?

Not only would dropping the ratatui layer slim down the dependencies it also
drops baggage (and complexity) from features we don't use. Other crates exist:
[bevy_crossterm](https://github.com/octotep/bevy_crossterm) does exactly this,
and [bevyterm](https://github.com/Mimea005/bevyterm) does something similar. I
don't know trade-offs for `bevyterm` as opposed to `bevy_crossterm` other than
the former intentionally does _not_ use a "separate runner" while the latter
does. I don't really know what the consequences of that are. In any case it
seems to be in line with what we're looking for -- a more direct integration to
Bevy from the terminal via crossterm.

> **bevy_crossterm uses a separate runner**
> It spins up its own event loop / thread to drive Bevy and handles terminal I/O
  separately from the main game loop. That means you have to coordinate states
  across two loops — your terminal input loop and Bevy's update loop. Your
  2026-08-27 note calls this out: it uses a "separate runner."
> 
> **bevyterm avoids a separate runner**:
> It integrates directly into Bevy's existing update/schedule loop without
  spawning an external runner to manage terminal events. All terminal
  input/cursor updates happen inside Bevy's normal systems, not via a sidecar
  loop.
> 
> Practical implications for our REPL: 
>
> - bevy_crossterm: More decoupled, but
  you have to manage synchronization between two loops (terminal vs. Bevy). Also
  out of date. 
> - bevyterm: Tighter Bevy integration, fewer scheduling/conflict
  issues (like the rustyline conflicts), simpler plugin-style
  architecture — which aligns with your goal of "a more direct integration to
  Bevy from the terminal via crossterm."

Let's skip over `bevy_crossterm` and focus on `bevyterm` since it's more in line
with our goals and approach.

## a closer look at `bevyterm`
See also [2026-08-27-bevyterm_research](2026-08-27-bevyterm_research.md)

Bevyterm is pretty slim as it is, and doesn't solve the kind of issues we identified
from previous work like scrolling or command parsing. Adding it as a dependency puts
us in the same spot as before, where we might be held up by conflicts or upstream
issues if we made it a straight up dependency.

The architecture patterns in Bevyterm are close to what I imagined for the REPL.
Let's see what we can learn from it to build our own REPL on top of crossterm
within the main execution schedule.

## developing the spec with ai
The `/wayfinder` skill did a pretty good job keeping the design process focused and
on track. It generated sample code that passes my sniff tests. I think we have
a good spec to go from now. It covers:

### Display Strategy Priority
  1. *Primary Target*: Sticky Prompt via DECSTBM scroll region (logs scroll above pinned prompt on main screen).
  2. *Fallback Target*: Full Alternate-Screen TUI if DECSTBM adds overwhelming cross-terminal edge-case complexity.

### Decisions so far
- [[01] Terminal Lifecycle and Panic Recovery](issues/01-terminal-lifecycle-and-panic-recovery.md): RAII `ReplTerminal` resource with `Drop` restoration, lightweight `std::panic` hook wrapper, and dynamic raw-mode toggle on REPL enable/disable.
- [[02] Crossterm Event Ingestion and Input Suppression](issues/02-crossterm-event-ingestion-and-input-suppression.md): Non-blocking `poll(Duration::ZERO)` in `ReplSet::Capture` with `Press | Repeat` filtering, modular `PromptKeymap`, Shift+Enter multiline, state-based input suppression, and toggle-key filtering.
- [[03] Sticky Prompt and DECSTBM Scroll Region](issues/03-sticky-prompt-and-decstbm-scroll-region.md): ANSI DECSTBM escape codes for row partitioning, change-detection prompt rendering in `ReplSet::Render`, and dynamic resize handling.
- [[05] Clap Command Parser and Observer Dispatch](issues/05-clap-command-parser-and-observer-dispatch.md): Shell-words tokenization, explicit required `to_event` mapping (eliminating silent argument loss and artificial `Default` bound), `bevy_repl_derive` support, and `Commands::trigger` observer dispatch.
- [[06] Derive Macro Ergonomics and Complexity](issues/06-derive-macro-ergonomics-and-complexity.md): Dual macro design (`#[repl_command]` attribute macro to automatically inject `clap::Parser`/`Event`/`Clone` derives alongside standard `#[derive(ReplCommand)]`), zero `Default` bound requirement, and feature gating.
- [[04] Tracing Subscriber Integration](issues/04-tracing-subscriber-integration.md): `repl_tracing_layer()` integration for Bevy's `LogPlugin`, scroll-region log positioning at row $H-1$, and automatic cursor restoration back to the prompt line.

### Not specified yet
- Multi-line / word-wrapped prompt reserving $N$ bottom rows for long commands.
- Status bar / gutter line (top or bottom) for FPS, entity counts, or custom debug diagnostics.
- Command history buffer and arrow-key navigation (`Up`/`Down` history stack).
- Key modifier chords (Ctrl, Alt, Shift) comprehensive mapping table.

### Out of scope
- Full Alternate-Screen TUI mode (scope is strictly the main screen sticky prompt).
- External background runner thread (bound to in-schedule execution per ADR-0001).
- Complex multi-widget rendering pipelines (no Ratatui replacement widgets).
