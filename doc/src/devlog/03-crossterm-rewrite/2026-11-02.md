# 2026-11-02 - Stepping Back: Intent, Assumptions, Questions

## Why step back

I started running the prototypes with prototype 0 and the plan stopped making
sense. The process was overconstrained, and that made it complicated:

- The rules say no prototype depends on another, but the list is numbered
  like a sequence, and what I actually want to watch is how one thing (the log
  pipeline) reacts as changes pile up.
- The list mixes different kinds of question: reading input, where output and
  logs go, parsing commands, and cost.
- Several prototypes overlap (1b and 2 both read keys in the schedule; 1c and
  6 both put logs next to a typed line; 8 has to hold before 1c or 6 can).
- I never wrote down what the plugin is for, or when and how it runs. The
  prototypes were testing assumptions about a plugin whose assumptions weren't
  stated.

The plan as it stood is kept on the `prototypes` branch so I can come back to
it. Today's work is on `dev-2026-11-02`.

## Plan for today

2. Write down the assumptions about how and when the plugin runs.
3. List the core questions that have to be answered before building.
4. Design one prototype per question, each one answering its question on its

## Intent

A Bevy app gets started from a terminal, with `cargo run` or the Bevy CLI.
Usually it opens a window where the app lives, and the logs keep streaming to
the terminal.

The other case is running it headless: no renderer, just the scheduler, the
game logic and the event system. The runtime doesn't need a renderer for that.
The logs still stream to the terminal.

In both cases I want a console in that terminal. Headless, there is no other
console, because nothing renders an egui one. And I don't want to maintain a
separate UI for a TUI. With no TUI, or as thin a TUI as possible, it stays
easy to maintain, and the console is always there in my terminal next to the
logs while the game runs. I don't need to open a separate menu.

What I'm after is the experience of a quake-style console, from a headless
app. The console is a manual control panel I can reach while the app runs. It
isn't a fundamental part of the app. It's there for debugging and the like: a
layer that gives access to the deep stuff, maybe instruments it, and doesn't
interfere with the app's core operation. The app should run as natively as
possible, and the changes and debugging I do through the console shouldn't
affect its state or performance.

Windowed, the console can take over the whole terminal. I can still see the
behavior, logs and debug information in the window, and the normal logs could
go to a file or another buffer. Headless, the logs are the only way to see
what's happening, so the terminal has to serve both the console and the logs.

What I picture being useful: logs stream to the terminal while the app runs
headless. I press a key (F3 or whatever) and in place of the logs I get a
prompt where I type a command, hit Enter and get a response. I press F3 again
and it goes back to the logs, and logging resumes.

## Relaxing earlier goals

- **No TUI at all may not be possible** for this. The F3 switch above is a
  TUI, if a thin one.
- **Logs staying in the terminal after exit** can be dropped if it has to be.
  My frustration was that all the logs vanished as soon as the app exited.
  What has to hold is that the log messages are preserved somewhere, a file
  for example, so I can review them after the app ends. A normal windowed app
  leaves them in the terminal, and I can just scroll up.

## Ratatui, reconsidered

Describing the two panes, I think I was too naive to say ratatui was
something we should get rid of. I wanted it gone because I wanted something
simpler and lower level, and I didn't want to maintain an entire UI system
separately from the app. But if all of that is contained in the plugin, the
user doesn't have to do any UI setup. That part is just something we have to
do. The design needs another look for what's realistic to build and what's
important.

Decided: ratatui comes back, since its UI is clearly necessary now.

## Research: are we reinventing the wheel?

Before designing the TUI, two things to check: whether bevyterm or something
like it already does this, and whether the Bevy Remote Protocol (BRP) makes a
TUI unnecessary.

**Terminal crates.**

- [bevyterm](https://github.com/Mimea005/bevyterm): 8 commits, Bevy 0.10, no
  releases, no rendering, an open to-do list. Its useful idea (no custom
  runner, poll crossterm in `First`) is what the crossterm rewrite already
  does. Nothing to reuse.
- [bevy_term](https://docs.rs/bevy_term): a `TerminalPlugin` with
  ratatui-style rendering into a `Frame` resource. No console or log pane.
  It's AGPL-3.0, so depending on it would make BevyREPL AGPL too.
- No crate does a console with a log pane inside a Bevy app's terminal.

**BRP** ([bevy_remote 0.20.1](https://docs.rs/bevy_remote/0.20.1)).

- JSON-RPC 2.0. `RemotePlugin` adds the methods, and `RemoteHttpPlugin`
  serves them over HTTP on `127.0.0.1:15702` by default. No authentication.
- The server runs as tasks on Bevy's `IoTaskPool` (hyper and async-io), with
  no extra OS thread. It works headless; rendering is an optional feature.
- Built-in methods inspect and change the world: `world.query`,
  `world.get_components`, `world.insert_components`, `world.get_resources`,
  `world.trigger_event`, `registry.schema`, `rpc.discover` and more.
  Components and resources have to be reflectable.
- Custom methods: `RemotePlugin::default().with_method("name", handler)`,
  where the handler is a system taking `In<Option<Value>>`, runs with
  exclusive `World` access, and returns a JSON result.
- Methods ending in `+watch` stream results as server-sent events.
- Existing clients: [bevy_brp_mcp](https://docs.rs/bevy_brp_mcp), an MCP
  server so AI assistants can drive a Bevy app. No terminal client for people
  turned up.

**What a BRP companion would mean.** The app runs exactly as it does today:
its terminal keeps Bevy's logs in scrollback, with no raw mode, no TUI and
no `custom_layer`. A separate client, started in a second terminal (or a tmux
split, or a second SSH session), is an ordinary line-editing CLI that sends
commands over BRP. Commands could stay clap and observers on the app side,
behind one custom method that takes the typed line and returns the output.

## Assumptions

1. A person is at the terminal that started the app, either at the machine
   itself or over SSH.
2. The app has to run without the console too, detached or with no terminal
   at all. The console is optional and never required for the app to run.
   When there's no terminal to interact with in that session, the console
   detects it and doesn't start, and the app carries on without it.
3. Two run modes, windowed and headless. Windowed, the window shows what the
   app is doing, so the console can have the whole terminal. Headless, the
   terminal is the only view, so it carries both the logs and the console.
4. The console doesn't change how the app runs. It doesn't change the app's
   state unless a command does so on purpose, and it doesn't cost noticeable
   performance.
5. Log messages are kept somewhere the person can review after the app exits.

## Scope for 1.0

- **Logs to a file are the app author's job.** If they want a log file, they
  set up a `custom_layer` on `LogPlugin` the normal way, as the Bevy examples
  do. The console never takes logs away from where they normally go. Logs
  staying in the terminal's scrollback after exit is a later feature, not
  1.0.
- **The console asks for one `LogPlugin` change: a `custom_layer`** that
  routes the logs, or a copy of the log stream, to the plugin. That's a
  reasonable thing to ask, and it isn't worth jumping through hoops to avoid
  it. "No changes to the base setup" was a naive design goal with no
  foundation to stand on. When the rules were written I imagined no setup
  changes at all; where reality says otherwise, reality wins.
- **The alternate screen is OK.** The logs reach the plugin (and a file, if
  the author sets one up), so the earlier requirement that output prints
  straight to the terminal is relaxed.
- **Runtime toggling is in.** I had it out of 1.0. I didn't want a full-screen
  console that toggles because I thought an always-visible prompt would be
  simpler and more usable, with REPL responses going out as log messages in
  the same streams as every other log. That may be too much complication for
  now. Toggling gets something working and usable before I settle how to do
  the always-visible version.
- **Piped input and output, and other advanced uses, are after 1.0.** I don't
  have a solid use case for them yet.

## Core questions

Draft, still being worked through.

1. **Does the terminal come back on every exit path when ratatui runs inside
   a Bevy app?** This one stands firm: however the app exits, the user's
   terminal is left exactly as it was before the app ran. A normal exit,
   Ctrl+C and a panic are all viable, safe ways to exit, and each one cleans
   the terminal up.
2. (Merged into 3.)
3. **Can the terminal hold two panes, a log pane and a console pane, switched
   with F3?** The
   log pane has a continuous history I can scroll up and down, from the past
   and as new logs come in. F3 brings up the console over it. I type, and the
   responses print to the console's own buffer. F3 again and the console goes
   away as if it had been covering the log pane, which kept recording the
   whole time. F3 once more and the console comes back with its buffer
   intact. Two separate screens, in terminal space. The log pane gets its
   lines from a `custom_layer` the app author adds (see Scope for 1.0), so
   the open question is drawing and switching the panes inside a running
   Bevy app.
4. ~~Can the plugin write logs to a file?~~ Answered: that's the app author's
   job, through `custom_layer` (see Scope for 1.0).
5. **Windowed, does each key go to whichever window has focus?** The terminal
   is usually still open behind the app window, and reachable on a second
   monitor or with Alt+Tab. With the terminal focused, F3 toggles the console
   and typing never reaches the app. With the app window focused, F3 belongs
   to the app only.
6. **Can a typed line become a command event handled by an observer, using
   clap, without the app exiting on a bad command?**
7. **With no terminal, does the plugin stay out of the way?** See assumption
   2.
8. **Does the console cost anything noticeable while it's closed?**

## Prototypes

Decided: prototype both and compare them side by side before choosing which
one to take further. First all the basics from the same terminal, accepting a
bunch of bugs and caveats. Then see how hard the same thing is over BRP. The
study gets recorded as it goes, and it's good practice for learning Bevy.

Draft of the study:

- **A. Same terminal.** A ratatui TUI inside the app: a log pane fed by a
  `custom_layer`, a console pane, F3 to switch, and the terminal restored on
  a normal exit, Ctrl+C and a panic.
- **B. Companion over BRP.** The app adds `RemotePlugin` and
  `RemoteHttpPlugin` and one custom method that takes a typed line. A
  separate client in a second terminal reads lines and sends them.
- **Same for both:** the same headless app logging at 1Hz, the same couple of
  commands parsed with clap and handled by observers, and the same checklist
  run on Windows and over SSH.
- **Compare on:** how much code each takes, what the app author has to add,
  what breaks, how it feels to use, and what it costs the app.

### The shared app: an analog clock

The smallest toy that shows the idea, with no terminal code in it. It's an
app someone made on its own, and the REPL gets added on top. It has a time
theme, which is a nod to my other projects.

I went through a shape grid first (a shape every second, filling a grid,
toggled between squares and triangles), then random positions with a
lifespan so it couldn't run away. Both were getting complicated. A clock is
bounded on its own, the programming is easy, and all of it is obvious.

- **Window:** a clock face with an hour hand and a minute hand. On every
  timer tick the minute hand moves one step, counting up to 60 and starting
  over. The hour hand counts up to 12 and starts over.
- **Logs:** every tick logs the time, so headless I still know what the clock
  is doing.
- **Headless too.** The app also runs without a renderer. The timer still
  ticks and the logs still print. The logs and `list` are the only view of
  the clock.

The commands, written as plain functions and an event in the app, not wired
to any input yet. Prototypes A and B each wire them up.

| Command | What I should see |
|---|---|
| `list` | The entities that exist, with their IDs, and the hands' positions. Matches the window. |
| `mark` | Spawns a mark on the dial where the minute hand is now, and logs it. The next `list` shows it with its ID. At most 60 positions, so it can't run away. |
| `toggle` | Triggers an event that switches the clock between ticking forward and backward in time. Both states are visible. |

A walkthrough that should work in both prototypes: watch it tick, `mark`,
`list` shows the mark, `toggle`, and the hand goes back past the mark.
