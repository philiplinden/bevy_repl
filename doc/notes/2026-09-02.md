# 2026-09-02 - Reconsidering Tracing & The Clean-Slate Architecture

## Context & Motivation

The current branch has accumulated significant complexity and scar tissue from combining three or four distinct architectural paths:
1. **Ratatui/TUI remnants**: Multi-stage scheduling sets and widget-era mental models.
2. **The Runtime Toggle spiral**: Trying to support F3 runtime enable/disable in headless apps without an OS window forced always-on raw mode, broke Ctrl+C, duplicated geometry math across six sites, and bloated the `Repl` resource.
3. **Logging seam friction**: Fighting Bevy's `LogPlugin` (`custom_layer` vs `fmt_layer` vs disabling it entirely) to prevent double-printing while keeping log level filters intact.
4. **Deferred event multiplexing**: Routing single keystrokes through `ReplBufferEvent` messages across separate system sets instead of direct, synchronous mutations.

Returning to the original vision in `doc/src/design/index.md` and the lessons from `bevyterm`, the essential crate only needs to do three things:
1. Initialize raw mode at startup (with panic and exit safety); restore it on exit.
2. Poll terminal events non-blockingly (`poll(Duration::ZERO)`) in `PreUpdate`, mutate the line buffer, and dispatch commands via `Commands::trigger` on `Enter`.
3. Pin the prompt to the bottom row using standard DECSTBM scroll margins (`\x1B[1;{H-1}r`) so output scrolls cleanly above it.

This raises a foundational architectural question: **What if we didn't use `tracing` at all?**

---

## What If We Dropped Tracing?

### 1. What This Looks Like
- **Zero tracing dependencies**: `bevy_repl` removes `tracing-subscriber` completely.
- **Pure Command/Response REPL**: Command handlers and the REPL print output directly via a lightweight helper (e.g. `repl_println!` or a method on the REPL resource) that handles `\r\n` and cursor placement.
- **`bevy_repl` completely ignores Bevy's log stream**: It does not initialize, intercept, or reroute `info!`, `warn!`, or `error!`.

### 2. The Pros
- **Dramatically simpler codebase**: Eliminates `MakeWriter`, `BoxedLayer`, `tracing-subscriber` registries, and all synchronization/timing issues around when Bevy's logging initializes.
- **Faster compilation & lighter dependency tree**: Drops `tracing-subscriber` and its heavy feature flags (`fmt`, `ansi`, `registry`).
- **No subscriber race conditions**: In Rust/Bevy, only one global tracing subscriber can ever be installed. If `bevy_repl` never touches the global subscriber, it can never conflict with user-configured loggers or `DefaultPlugins`.

### 3. The Catch: What Happens When the App Calls `info!("hello")`?
In raw mode with a DECSTBM scroll region:
- **Cursor Collision**: After `render_prompt` runs, the terminal cursor is parked at row $H$, column $X$ (on the prompt line).
- When Bevy's default logger writes to `stdout`, it writes wherever the cursor currently is. If the cursor is on row $H$, standard logging will print **directly on top of the prompt line** and push the screen upward, clobbering the prompt until the next frame redraws it.
- **Raw Mode Stair-stepping**: On Unix terminals in raw mode, `\n` only moves the cursor down one row—it does *not* return to column 0 without an explicit carriage return `\r`. Standard Bevy log output using plain `\n` causes diagonal "stair-stepping" across the screen.

## How Terminal Output Interacts with Bevy's Native Logging

If in-terminal log streaming is desired, the terminal viewport must be partitioned:

```
┌─────────────────────────────────────────────────────────┐
│ Row 1 .. H-1: DECSTBM Scroll Region                     │
│                                                         │
│ [INFO] Game initialized                                 │
│ [WARN] Low FPS detected                                 │
│ [INFO] Spawned entity 42                                │ <- Logs stream & scroll here
├─────────────────────────────────────────────────────────┤
│ Row H: Pinned Prompt Line                               │
│ > spawn enemy --count 3█                                │ <- Cursor parked here
└─────────────────────────────────────────────────────────┘
```

### Coordinated Output Requirements
1. **DECSTBM Margin**: An escape code (`\x1B[1;{H-1}r`) tells the terminal that scrolling only happens between row 1 and row $H-1$.
2. **Coordinated Output Writer**: Whenever text is printed (command results or Bevy logs):
   - Cursor moves to row $H-1$, column 0.
   - Writes the text with explicit `\r\n`.
   - The terminal scrolls row $1 \dots H-1$ up naturally, leaving row $H$ (the prompt) untouched.
   - The prompt line is then drawn or refreshed at row $H$.

### Plugging into Bevy's `LogPlugin`
Bevy's `LogPlugin` provides a designated substitution seam (`fmt_layer`):
```rust
app.add_plugins(
    DefaultPlugins.set(LogPlugin {
        fmt_layer: Some(Box::new(|_app| Some(bevy_repl::make_repl_layer()))),
        ..default()
    })
);
```

## The 3 Architectural Options

| Option | Complexity | Log Experience | Best For |
| :--- | :--- | :--- | :--- |
| **A. Pure REPL (No Tracing)** | **Minimal** (0 tracing deps) | Standard `info!` will clobber prompt line unless logs are disabled or redirected to a file. Command output uses `repl_println!`. | Pure CLI tools, benchmarks, games redirecting logs to files, or minimal headless runners. |
| **B. Pure Crossterm Core + Optional Tracing Adapter (`feature = "tracing"`)** | **Low-Medium** (default enabled) | `bevy_repl` core has zero tracing dependencies; enabling the `tracing` feature provides `make_repl_layer()` for Bevy's `LogPlugin.fmt_layer`. | Cleanest design: decoupled core crate, seamless log streaming when desired. |
| **C. Alternate Screen REPL** | **Low** | When REPL starts, it enters crossterm's alternate screen buffer (`EnterAlternateScreen`). Logs stay on the main screen, REPL runs on its own dedicated screen. | Terminal-first tools or dev overlays where REPL and logs don't share the same viewport. |

---

## Recommended Direction

**Option B (Pure Crossterm Core + Optional Tracing Feature)**:
1. Build the core crate around raw `crossterm` and `clap` with no `tracing-subscriber` dependency.
2. If `feature = "tracing"` is enabled, expose a clean, minimal `ReplMakeWriter` layer that users can pass to `LogPlugin.fmt_layer`.
3. This keeps the core REPL clean and testable, while still supporting unified terminal output when needed.
